## Design summary

- **One database, one schema, both apps.** No table, column or policy depends on which app calls. The School App, the Student App (student mode) and the Student App (parent mode) differ only in route family and request context.
- **Tenant isolation, three layers.** (1) Guard: active membership + permission, or an active guardian link for parent routes. (2) RLS on every school table: tenant policy, plus restrictive policies so students and parents see only their own student/section and never staff-only tables. (3) **Composite foreign keys** `(school_id, x_id)` on every school-to-school reference, because foreign-key checks ignore RLS: a row in school A can never point at a row in school B.
- **Identity.** Global `users`. Staff and students log in with a school-issued username (`sch0001e0001`, `sch0001s0001`) and password; temp passwords are hashed once in `credentials` with a forced change. Principal and parent log in with mobile + OTP (`otp_challenges`, SECURITY DEFINER only). Platform staff live in `platform_staff`.
- **Parents.** Guardians (legal relationship and contact) live on the student record (`student_guardians`). Staff issue a single-use, expiring code per guardian (`guardian_link_codes`, stored hashed); a parent with an OTP-verified mobile redeems it with the school code and admission number, which creates `parent_student_links`. Children across schools are supported. A username, admission number or guardian mobile alone never grants access.
- **Student messaging (V1.2).** One-way, read-only for students: a full-school group and one group per class-section, resolved on the server from the student's membership and active enrollment. One table (`student_messages`) plus an optional unread-badge row per student; no group, membership, reply or attachment tables.
- **Designations (V1.2).** Non-teaching staff types are configured per school (`staff_designations`) and never grant permissions; roles stay the only source of authorization.
- **Approvals.** One generic engine (`approval_requests` + append-only `approval_actions`) for the 8 approved V1.2 types; real approver recorded, reason required on reject, resubmission as a new version.
- **History is never overwritten:** enrollments per year, teacher assignments with `valid_from/valid_to` (trigger-guarded), timetable versions, result-set versions, attendance corrections, approval actions, audit logs.
- **Cheap by default.** Generic tables replace one-off ones (holidays in `calendar_events`, periods computed from `school_timings`, conflicts computed, transitions and assignment changes as approval payloads). Only three tables are partitioned.

## Conventions

| Topic           | Rule                                                                                                                                                                                     |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Keys            | UUIDv7 generated by the app; every referenced school table has `@@unique([schoolId, id])`                                                                                                |
| Tenant column   | `school_id uuid NOT NULL` on every school table; nullable only on `credential_issuances`, `school_verification_requests`, `notifications`, `outbox_events`, `audit_logs` (global events) |
| Timestamps      | `timestamptz`; `created_at`, `updated_at`, `created_by` everywhere; `updated_by` where edits are audited                                                                                 |
| Dates           | School-local `date` columns for attendance, leave, timetable and exams; "today" uses `schools.timezone` (default `Asia/Kolkata`)                                                         |
| Soft delete     | None. Students, staff and memberships use status values; history tables are append-only                                                                                                  |
| Enums vs tables | Enums for stable sets; tables for configurable lists (`departments`, `staff_designations`, `leave_types`); free text for exam types and categories                                       |
| Actor columns   | Plain user ids, no foreign key (as today)                                                                                                                                                |
| Money           | No money columns in V1 (fees out). The integer-paise rule stays for later                                                                                                                |
| Migrations      | Expand-then-contract. Existing tables only gain columns; no renames (`audit_logs.target_type/target_id` stay)                                                                            |

## Partitioning and size (pilot: 100 schools, ~2.5 lakh users)

| Table                | Partitioning                                      | Why                                                                                                                   |
| -------------------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `student_attendance` | Monthly range on `attendance_date`                | ~4.4 crore rows a year                                                                                                |
| `notifications`      | Monthly range on `created_at`, drop after 90 days | Crores of rows a year, short-lived                                                                                    |
| `audit_logs`         | Monthly range on `created_at`                     | Tens of millions a year; retention by dropping partitions. Converted now, while no staging/production database exists |

Watch: `homework_completions` (up to ~2 crore rows a year if every student is tracked for every homework). Not partitioned in V1.

## Migration plan for V1.2 (draft only; nothing is migrated in this update)

Each slice copies its models from the draft into `apps/api/prisma/schema.prisma` as today (expand-then-contract; no destructive change to existing migrations).

1. **Slice 3:** `staff_designations` with RLS, the case-insensitive unique index, no app-role DELETE, and the `staff` trigger that rejects inactive designations. `approval_type` is created with the eight V1.2 values from the start (the enum does not exist in the live schema yet, so no rename is needed).
2. **Slice 3, contract step for roles:** the live `role` enum still has `office_clerk`, `accountant`, `other_staff`. (a) Migration: delete their `role_permissions` rows and add `CHECK (role NOT IN (...))` on `school_memberships` (expand, safe). (b) A later release, after checking no membership uses them: recreate the enum without the three values (`ALTER TYPE ... RENAME`, create the new type, `ALTER COLUMN ... TYPE ... USING role::text::role`, drop the old type) in one transaction. Update `packages/shared-types` roles in the same PR.
3. **Slice 4:** `students.admission_number` is NOT NULL from creation (the table is new); `guardian_link_codes` (+ partial unique, column-level grant that hides `code_hash`, no DELETE) and `auth_redeem_link_code` (SECURITY DEFINER, schema-qualified names, `search_path = pg_catalog`). New secret `LINK_CODE_HASH_SECRET` (≥ 32 bytes) in `.env.example` and config validation.
4. **Slice 5:** `student_messages` (CHECKs, column-level UPDATE grant on withdraw columns only, no DELETE), `student_message_read_states` if OPEN-QUESTIONS M3 stays yes, the R-msg restrictive policy, and outbox event `student_message.published`.
5. **Never created:** `documents`, `document_access`, `file_purpose = admin_document`, any IT-staff or discipline table.
