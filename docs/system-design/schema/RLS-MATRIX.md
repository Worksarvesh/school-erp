# RLS policy matrix (draft V1.1)

Row Level Security is the second wall behind the API guards. It does **not** depend on which app is calling (School App or Student App): it depends only on the request context the API sets. Policies are hand-written SQL appended to each Prisma migration.

## Request contexts

Every request runs in one transaction that sets transaction-local settings (`set_config(..., true)`) through helpers in `apps/api/src/database/school-context.ts`. No other code calls `set_config`.

| Helper                                                      | Sets                                                                                          | Used by                                                                                                                                                                  |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `withSchoolContext(schoolId)` (exists)                      | `app.school_id`, `app.user_id`, `app.access = 'member'`                                       | Staff on `/v1/schools/:schoolId/...` after `SchoolAccessGuard`                                                                                                           |
| `withStudentContext(schoolId, studentId, sectionId)` (new)  | the above + `app.access = 'self'`, `app.student_id`, `app.section_id`                         | A student member on `/v1/schools/:schoolId/me/...`                                                                                                                       |
| `withGuardianContext(schoolId, studentId, sectionId)` (new) | `app.school_id`, `app.user_id`, `app.access = 'guardian'`, `app.student_id`, `app.section_id` | A parent on `/v1/schools/:schoolId/children/:studentId/...`, after the guard finds an **active** `parent_student_links` row for (caller, student, school). No link = 404 |
| `withUserContext()` (exists)                                | `app.user_id` only                                                                            | "My own rows" across schools: `/v1/me`, sessions, push tokens, notifications, `GET /v1/me/children`                                                                      |
| `withPlatformContext(role)` (new)                           | `app.user_id`, `app.platform_role`                                                            | `/v1/platform/...` routes after the platform guard. Every call writes an audit row                                                                                       |

SQL helpers (all `STABLE`, read with `nullif(current_setting(..., true), '')`): `current_school_id()`, `current_app_user_id()` (exist), plus `current_access()` (null treated as `member`), `current_student_id()`, `current_section_id()`, `current_platform_role()`.

## Policy codes

| Code        | Meaning                              | SQL shape                                                                                                            |
| ----------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| **T**       | Tenant (permissive)                  | `USING (school_id = current_school_id()) WITH CHECK (school_id = current_school_id())`                               |
| **O**       | Own rows (permissive)                | `user_id = current_app_user_id()` (or `recipient_user_id`, `principal_user_id`)                                      |
| **SM**      | Same-school members (users)          | `EXISTS (membership of users.id in current_school_id())` (exists today)                                              |
| **MS**      | My schools (schools, read)           | `EXISTS (active membership of current_app_user_id())` (exists today)                                                 |
| **P**       | Platform (permissive)                | `current_platform_role() IS NOT NULL` (or a specific role)                                                           |
| **G-allow** | Readable by students and parents     | No extra policy: tenant policy is enough (school reference data)                                                     |
| **G-deny**  | Staff-only table (restrictive)       | `AS RESTRICTIVE USING (current_access() = 'member')`. Students and parents never see a row even if the API has a bug |
| **R-stu**   | One student only (restrictive)       | `AS RESTRICTIVE USING (current_access() = 'member' OR student_id = current_student_id())` (`students` uses `id`)     |
| **R-sec**   | One section only (restrictive)       | `AS RESTRICTIVE USING (current_access() = 'member' OR section_id = current_section_id())`                            |
| **R-pub**   | Published results only (restrictive) | `AS RESTRICTIVE USING (current_access() = 'member' OR EXISTS (published result set))`                                |
| **D**       | SECURITY DEFINER only                | No grants to the app role; reached only through narrow functions (pattern of `auth_find_login_user`)                 |
| append-only | No changes after insert              | `REVOKE UPDATE, DELETE, TRUNCATE` from `school_erp_app` (+ trigger on `audit_logs`)                                  |

Rules that still apply on top: the guard checks permission keys (never role names); filters like "only my assigned sections" for teachers, "published only" for timetables, and notice audiences are **app checks**, listed per table below.

## Parent access across schools

1. Parent signs in with mobile + OTP. The verified phone is the user's `users.phone`.
2. `auth_sync_parent_links(user_id)` (SECURITY DEFINER) finds every **active** `student_guardians` row with that mobile, in any school, and upserts `parent_student_links`. Links whose guardian row is no longer active (removed, or mobile changed) are revoked.
3. `GET /v1/me/children` runs in `withUserContext()` and reads `parent_student_links` (policy **O**) plus each child's name, class and section, and the school name and logo, through one SECURITY DEFINER read (`parent_children_summary`). It never opens a school context.
4. Each child screen calls `/v1/schools/:schoolId/children/:studentId/...`. The guard checks the link, then runs `withGuardianContext`. From then on the request reads only that school (**T**), only that student (**R-stu**) or section (**R-sec**), and never staff-only tables (**G-deny**).
5. Two children in two schools are two separate requests and two separate RLS contexts. They never meet in one query.

A username alone never grants access: parents have no username, and links come only from a verified OTP mobile.

## Isolation tests to add (`apps/api/test/isolation.int-spec.ts` and new specs)

The existing suite already discovers every route and every RLS table, and fails if a table lacks RLS or fixture rows. For V1.1 it also needs:

| #   | Test                                                                                                                                                                                     |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Fixture rows in both schools for all 65 tables (the suite enforces this)                                                                                                                 |
| 2   | Every school route: 401 signed out, 404 from another school, works for an all-roles member (existing rule)                                                                               |
| 3   | Every `/children/:studentId` route: 404 for a parent with no link, 404 for a revoked link, 404 for the parent's child in school A when called with school B's id, 200 for an active link |
| 4   | Guardian context: raw SELECT on each **G-deny** table returns 0 rows; on each **R-stu** table returns only the linked student's rows                                                     |
| 5   | Student context: same as 4 for `self`, plus a student cannot read another student's attendance, marks or results in the same section                                                     |
| 6   | Unpublished `result_sets` / `student_results` are invisible in guardian and self context                                                                                                 |
| 7   | Composite foreign keys: inserting a row in school A that points at school B's section/student/staff fails (FK error), even as the owner role                                             |
| 8   | Platform routes: 401 signed out, 403 for a school member who is not platform staff, audit row written for every call                                                                     |
| 9   | `audit_logs`: UPDATE and DELETE fail for the app role **and** the owner role (trigger)                                                                                                   |
| 10  | `teacher_assignments`: updating any column other than `valid_to`, or reopening a closed row, fails (trigger)                                                                             |
| 11  | Parent link sync: removing a guardian or changing its mobile revokes the link on the next login and on the change itself                                                                 |
| 12  | New public routes (OTP send/verify, directory search) on the `NON_SCHOOL_ROUTES` allowlist as `public`, each tested for no account enumeration                                           |
