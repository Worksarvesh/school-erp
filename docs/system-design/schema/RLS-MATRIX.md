# RLS policy matrix (draft V1.2)

Row Level Security is the second wall behind the API guards. It does **not** depend on which app is calling (School App or Student App): it depends only on the request context the API sets. Policies are hand-written SQL appended to each Prisma migration.

## Request contexts

Every request runs in one transaction that sets transaction-local settings (`set_config(..., true)`) through helpers in `apps/api/src/database/school-context.ts`. No other code calls `set_config`.

| Helper                                                      | Sets                                                                                                                                                             | Used by                                                                                                                                                                  |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `withSchoolContext(schoolId)` (exists)                      | `app.school_id`, `app.user_id`, `app.access = 'member'`                                                                                                          | Staff on `/v1/schools/:schoolId/...` after `SchoolAccessGuard`                                                                                                           |
| `withStudentContext(schoolId, studentId, sectionId)` (new)  | the above + `app.access = 'self'`, `app.student_id`, `app.section_id`, `app.enrollment_start` (all from the caller's active enrollment, looked up on the server) | A student member on `/v1/schools/:schoolId/me/...`                                                                                                                       |
| `withGuardianContext(schoolId, studentId, sectionId)` (new) | `app.school_id`, `app.user_id`, `app.access = 'guardian'`, `app.student_id`, `app.section_id`                                                                    | A parent on `/v1/schools/:schoolId/children/:studentId/...`, after the guard finds an **active** `parent_student_links` row for (caller, student, school). No link = 404 |
| `withUserContext()` (exists)                                | `app.user_id` only                                                                                                                                               | "My own rows" across schools: `/v1/me`, sessions, push tokens, notifications, `GET /v1/me/children`                                                                      |
| `withPlatformContext(role)` (new)                           | `app.user_id`, `app.platform_role`                                                                                                                               | `/v1/platform/...` routes after the platform guard. Every call writes an audit row                                                                                       |

SQL helpers (all `STABLE`, read with `nullif(current_setting(..., true), '')`): `current_school_id()`, `current_app_user_id()` (exist), plus `current_access()` (null treated as `member`), `current_student_id()`, `current_section_id()`, `current_platform_role()`, and (V1.2) `current_enrollment_start()` (the `started_on` of the student's active enrollment, set by `withStudentContext` as `app.enrollment_start`) and `can_publish_student_message(audience, section_id)` (below). All schema-qualified, as the existing rule requires.

## Policy codes

| Code            | Meaning                                          | SQL shape                                                                                                                                                                                                                                                                                                            |
| --------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **T**           | Tenant (permissive)                              | `USING (school_id = current_school_id()) WITH CHECK (school_id = current_school_id())`                                                                                                                                                                                                                               |
| **O**           | Own rows (permissive)                            | `user_id = current_app_user_id()` (or `recipient_user_id`, `principal_user_id`)                                                                                                                                                                                                                                      |
| **SM**          | Same-school members (users)                      | `EXISTS (membership of users.id in current_school_id())` (exists today)                                                                                                                                                                                                                                              |
| **MS**          | My schools (schools, read)                       | `EXISTS (active membership of current_app_user_id())` (exists today)                                                                                                                                                                                                                                                 |
| **P**           | Platform (permissive)                            | `current_platform_role() IS NOT NULL` (or a specific role)                                                                                                                                                                                                                                                           |
| **G-allow**     | Readable by students and parents                 | No extra policy: tenant policy is enough (school reference data)                                                                                                                                                                                                                                                     |
| **G-deny**      | Staff-only table (restrictive)                   | `AS RESTRICTIVE USING (current_access() = 'member')`. Students and parents never see a row even if the API has a bug                                                                                                                                                                                                 |
| **R-stu**       | One student only (restrictive)                   | `AS RESTRICTIVE USING (current_access() = 'member' OR student_id = current_student_id())` (`students` uses `id`)                                                                                                                                                                                                     |
| **R-sec**       | One section only (restrictive)                   | `AS RESTRICTIVE USING (current_access() = 'member' OR section_id = current_section_id())`                                                                                                                                                                                                                            |
| **R-pub**       | Published results only (restrictive)             | `AS RESTRICTIVE USING (current_access() = 'member' OR EXISTS (published result set))`                                                                                                                                                                                                                                |
| **R-msg**       | Student message feed (restrictive)               | `AS RESTRICTIVE FOR SELECT USING (current_access() = 'member' OR (current_access() = 'self' AND status = 'published' AND published_at >= current_enrollment_start() AND (audience = 'school' OR section_id = current_section_id())))`. Guardian context matches neither branch, so parents see nothing (decision M2) |
| **R-send**      | Who may publish (restrictive INSERT)             | `AS RESTRICTIVE FOR INSERT WITH CHECK (sender_user_id = current_app_user_id() AND public.can_publish_student_message(audience, section_id))` (decision M1, evaluated at insert time)                                                                                                                                 |
| **R-self-only** | Student's own row, no staff access (restrictive) | `AS RESTRICTIVE USING (current_access() = 'self' AND student_id = current_student_id())`. Unlike R-stu it also denies every member context                                                                                                                                                                           |
| **D**           | SECURITY DEFINER only                            | No grants to the app role; reached only through narrow functions (pattern of `auth_find_login_user`)                                                                                                                                                                                                                 |
| append-only     | No changes after insert                          | `REVOKE UPDATE, DELETE, TRUNCATE` from `school_erp_app` (+ trigger on `audit_logs`)                                                                                                                                                                                                                                  |

Rules that still apply on top: the guard checks permission keys (never role names, never designations); a key is held when the caller's active membership roles grant it **or** an open `user_permission_grants` row exists for (school, user, key) (V1.2). Filters like "published only" for timetables and notice audiences are **app checks**, listed per table below. Student-message sending rights are enforced in the database (R-send), not only in the app.

## Parent access across schools (V1.2: link codes)

1. Principal or Admin (`guardians.link_codes.issue`) issues a code for one active guardian of one student (`guardian_link_codes`; shown once; only its HMAC is stored; issuing a new code revokes the open one).
2. Parent signs in with mobile + OTP. The verified phone is the user's `users.phone`. Signing in alone links nothing.
3. Parent enters school code + admission number + link code. `auth_redeem_link_code(user_id, school_code, admission_number, code)` (SECURITY DEFINER, `search_path = pg_catalog`) finds the school and student, compares the code in constant time against open codes for that student, counts a wrong attempt on that student's open codes, and on success marks the code used and inserts an **active** `parent_student_links` row (decision L1: no Admin confirmation) in the same transaction, plus an audit row. Every failed redemption is audited too (`parent_link.redeem_failed`: actor, IP, failure class; never the typed code). Every failure (unknown school, unknown admission number, wrong, expired, used or locked code) returns the same generic error. Per-user and per-IP rate limits apply before the function is called.
4. `GET /v1/me/children` runs in `withUserContext()` and reads `parent_student_links` (policy **O**) plus each child's name, class and section, and the school name and logo, through one SECURITY DEFINER read (`parent_children_summary`). It never opens a school context.
5. Each child screen calls `/v1/schools/:schoolId/children/:studentId/...`. The guard checks for an **active** link, then runs `withGuardianContext`. From then on the request reads only that school (**T**), only that student (**R-stu**) or section (**R-sec**), and never staff-only tables (**G-deny**).
6. Two children in two schools are two separate requests and two separate RLS contexts. They never meet in one query.

A username, an admission number or a guardian mobile alone never grants access: only a redeemed single-use code does.

## Student messaging (V1.2, decisions M1-M5)

1. **Reading.** `GET /v1/schools/:schoolId/me/messages` runs in `withStudentContext`, which looks up the caller's student row and **active** enrollment on the server and sets `app.student_id`, `app.section_id` and `app.enrollment_start`. The route takes no school-, class-, section- or group-id parameter that affects access; a `group` filter accepts only `school` or `section`. **R-msg** returns only published rows of the school group and the current section, published on or after the active enrollment's `started_on`, even if the query forgets the filter.
2. **Section changes (M4).** When the active enrollment changes (promotion, section transfer, re-admission), the next request carries the new section and the new `started_on`. The old section's messages stop being readable at once, and messages of the new section sent **before** the student joined it are not shown. A student with no active enrollment (status `admitted`, `inactive`, `transferred`) sees no messages.
3. **Parents (M2).** No route and no RLS branch for guardian context: parents see no student messages in V1.
4. **Sending (M1).** `POST /v1/schools/:schoolId/student-messages` runs in `withSchoolContext`. The guard checks that the caller holds a publish key for the audience; the database then checks the exact right through **R-send** at insert time:

   ```sql
   -- public.can_publish_student_message(p_audience, p_section_id): STABLE, schema-qualified names
   -- school audience: an active principal / vice_principal / school_admin membership in current_school_id()
   -- section audience:
   --   (a) an active principal / vice_principal / school_admin membership (any section of the school), or
   --   (b) an active teacher membership AND an open teacher_assignments row (valid_to IS NULL) for
   --       (the caller's staff row, p_section_id), or
   --   (c) an active non_teaching_staff membership AND an open student_message_section_grants row
   --       (revoked_at IS NULL) for (the caller's staff row, p_section_id)
   ```

   Closing an assignment or revoking a grant therefore stops new messages from the next insert, with no cache. `sender_user_id` must equal `current_app_user_id()` and `sender_role` must be a role the caller actually holds (CHECK in the same function); both come from the session, never the body. Non-teaching staff never pass the school-audience branch.

5. **Withdraw and retention (M5).** Withdraw is an UPDATE of status and withdrawn_* columns only (column-level grant); the body is never updated. A worker job sets `archived` on messages of academic years older than `schools.student_message_retention_years` (proposed default 1). The app role has no DELETE on the table; hard deletion happens only through a documented data-erasure procedure (DPDP), outside normal operation, and is audited.
6. **Unread badge (M3).** `student_message_read_states` is readable and writable only in the student's own self context (R-self-only). No staff route, report or export reads it; senders never learn who read a message.
