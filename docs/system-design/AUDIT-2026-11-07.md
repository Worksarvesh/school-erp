# Audit of existing work against V1.1 (2026-11-07)

Phase A of the "audit, then design the full schema" task. Read-only: nothing in the repo was changed except this file.

- Branch audited: `docs/v1.1-audit`, cut from `feat/auth-sessions` at `9d3b71e` (slice 2A, not yet merged to `main`).
- Authority order used (newest first): V1.1 locked decisions (task prompt, section 3) > Figma file + Graphic Design Scope Report > `docs/system-design/*` > code.
- "Not found" means a search of all tracked files found nothing.

## Summary

- **What exists:** a solid foundation, not features. Tenancy core (schools, users, memberships, permissions, RLS, isolation test suite) and slice 2A (password login, rotating refresh sessions, append-only audit log, error shape). 8 tables, 4 enums, 3 migrations, 12 HTTP routes. No academic, people, attendance, timetable, exam, approval, notice or notification tables exist.
- **Biggest conflicts with V1.1:** (1) parent access: the docs forbid phone matching and plan link codes; V1.1 makes mobile + OTP matching the only parent path. (2) login: code logs in by phone/email + password and has no username; V1.1 needs username login for staff/students and OTP login for Principal/Parent. (3) fees, SMS/email channels and notification preferences are built into the design, CLAUDE.md and the OTP step-up types; V1.1 removes them. (4) role list has `office_clerk`, `accountant`, `other_staff`, which V1.1 does not have, and no platform roles.
- **Missing inputs:** `School_ERP_Graphic_Design_Scope_Report_V1.pdf` is not in the repo. The Figma file could only be read at page level (the Figma MCP Starter-plan call limit was hit), so frame names are not yet known.
- **Blocking questions** are at the end (section A8).

## A3. Database as implemented

### Tables

| Table                | Tenant column        | RLS policies                                                                                             | Notes                                                                                                                                                                                                                   |
| -------------------- | -------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schools`            | is the tenant (`id`) | `school_isolation` (id = current school); `member_schools` (SELECT, user has active membership)          | Columns: `name`, `code` (unique, free text e.g. `DEMO-SUNRISE`), `udise_code` (unique, nullable), `status`, `shard_key`. **No** address, PIN, logo, contact, verification state                                         |
| `users`              | global               | `visible_users` (self, or member of current school); `auth_lookup` (SELECT for `school_erp_auth_lookup`) | `full_name`, `phone` (E.164 CHECK, unique), `email` (lower-case CHECK, unique), `status` (`active`/`disabled`). **No** username, `must_change_password`, `last_login_at`                                                |
| `school_memberships` | `school_id`          | `school_isolation`; `own_memberships` (SELECT by `app.user_id`)                                          | Unique `(user_id, school_id, role)`; index `(school_id)`                                                                                                                                                                |
| `permissions`        | global               | none (app role: read only, write revoked)                                                                | 2 rows: `school.read`, `members.read`                                                                                                                                                                                   |
| `role_permissions`   | global               | none (app role: read only)                                                                               | 13 rows                                                                                                                                                                                                                 |
| `credentials`        | per user             | `own_credentials`                                                                                        | `password_hash`, `password_changed_at`. A user without a row cannot log in                                                                                                                                              |
| `sessions`           | per user             | `own_sessions`; `auth_lookup` (SELECT id, user_id)                                                       | Hashed refresh tokens, `previous_token_hash`, device name, expiry, revoke reason                                                                                                                                        |
| `audit_logs`         | `school_id` nullable | `school_read` (SELECT own school); `append` (INSERT own school or null)                                  | Columns: `actor_user_id`, `action`, `target_type`, `target_id`, `ip`, `metadata` JSONB. UPDATE/DELETE/TRUNCATE revoked from app role. Indexes `(school_id, created_at)`, `(actor_user_id, created_at)`. Not partitioned |

### Enums

`role` (10 values: principal, school_admin, vice_principal, teacher, non_teaching_staff, office_clerk, accountant, student, parent, other_staff) · `membership_status` (invited, active, suspended, revoked) · `school_status` (active, suspended) · `user_status` (active, disabled).

### Functions and roles

- `current_school_id()`, `current_app_user_id()` (tenancy migration).
- `auth_find_login_user(text)` → `(user_id, status)` by exact phone **or email**; `auth_find_session_user(uuid)`. SECURITY DEFINER, owned by `school_erp_auth_lookup`, EXECUTE only for `school_erp_app` (auth migration).
- DB roles: `school_erp_owner`, `school_erp_app`, `school_erp_auth_lookup` (`docker/postgres/init/01-roles.sh`).
- Note: tables use `ENABLE` (not `FORCE`) ROW LEVEL SECURITY. Safe today because the app role is not the owner; the owner role (migrations, seed) bypasses RLS.

### Documented but not implemented

From design §6 and `CLAUDE.md`: `academic_sessions`, `classes`, `sections`, `subjects`, `class_subjects`, `students`, `student_guardians`, `enrollments`, `attendance_records`, `timetable_slots`, `homework`, `homework_submissions`, `exams`, `exam_results`, `notices`, `notifications`, `device_tokens`, `files`, `outbox_events`, `otp_challenges`, `school_claims`, custom field definitions, `fee_structures`, `invoices`, `invoice_items`, `receipts`, `payments`. **None exist.**

## A7. Risks

### Security

| #   | Risk                                           | Why it matters                                                                                                                                              | Mitigation to design in Phase B                                                                                                                                                                                                                                |
| --- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S1  | **Parent access by mobile match**              | A guardian mobile typed wrong by Admin hands a stranger a child's data after a normal OTP. The old design banned this for exactly this reason (design §5.2) | OTP to that exact number is the proof of possession; audit every guardian mobile add/change; notify the old number on change (push/in-app); show the school name before revealing the child; limit guardians per student; rate-limit OTP per number and per IP |
| S2  | Principal and Parent cannot log in without OTP | OTP is not built (`otp.ts`), and V1.1 gives them no password path                                                                                           | Decide whether a dev/staging-only OTP stub is acceptable before real SMS (A8 Q1)                                                                                                                                                                               |
| S3  | Account enumeration on parent login            | V1.1 says "number not found: generic message, no OTP sent" — the absence of an SMS tells the user the number is unknown                                     | Accept (V1.1 explicit) but keep the screen response identical and rate-limit per IP/number                                                                                                                                                                     |
| S4  | Plain-text phone numbers                       | Parent login needs exact phone lookup; guardian mobiles now also live on student records                                                                    | Keep normalised E.164 + unique index; record in the DPDP review list (already open)                                                                                                                                                                            |
| S5  | Usernames are guessable (`sch0001s0001`)       | Sequential usernames make password spraying easier                                                                                                          | Keep per-identifier failure limits (exist in `login-failure-limiter.ts`); move limits to Redis before multiple API instances; forced first-login change                                                                                                        |
| S6  | Platform staff path not built                  | Verifier approval and Super Admin principal reset need cross-school reads                                                                                   | Separate role + routes, every access audited (design §3)                                                                                                                                                                                                       |
| S7  | Audit reads too broad                          | `audit_logs` policy lets any school context read all school rows                                                                                            | Role-scoped read rules (A5 #29)                                                                                                                                                                                                                                |

### RLS

- **Parent reads cross schools.** A parent is not a member of the school, so `app.school_id` policies alone do not grant access. Recommended: a `parent_student_links` table (user ↔ student ↔ school) written when OTP verification matches a guardian mobile, plus user-scoped SELECT policies keyed on `current_app_user_id()` — the same pattern as the existing `own_memberships` policy. Avoid policies that join on phone text at query time (slow, fragile).
- Student self-access (own attendance, results, homework) needs "own rows" policies too, not just school-wide ones.
- Every new table needs fixture rows in `test/isolation.int-spec.ts` (it fails otherwise) — real cost per table, which argues for fewer tables.

### Cost and scale (pilot: 100 schools, ~2.5 lakh users)

Rough sizes, illustrative only:

| Table                    | Estimate                                                               | Note                                                                   |
| ------------------------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Student attendance       | ~2 lakh students × ~220 days ≈ **4.4 crore rows/year**                 | Above 10 million; monthly range partitions (design §6 already says so) |
| `audit_logs`             | Several rows per write action across all staff ≈ tens of millions/year | Partition by month, set retention (DPDP review)                        |
| `notifications` (in-app) | Every notice/homework/result fans out per recipient ≈ crores/year      | Retention window (e.g. 90 days) + partition or periodic purge          |
| Timetable entries, marks | Hundreds of thousands to low millions                                  | Fine unpartitioned                                                     |

Supabase plan size and connection limits are unverified (hosting is on hold); keep to plain Postgres features so either host works.

## A9. Repo structure (added 2026-11-07)

Full analysis: [REPO-STRUCTURE.md](REPO-STRUCTURE.md). Short version:

- Today `apps/mobile` and `apps/web` are README-only placeholders (`apps/mobile/README.md`, `apps/web/README.md`); `pnpm-workspace.yaml` globs `apps/*` and `packages/*`. Splitting mobile into `apps/school-app` + `apps/student-app` moves one README and breaks no code; five docs need text updates.
- Recommended: one monorepo, one API, one database, two Expo apps, shared packages (option B). Separate backends (option C) would break the single-database rule.
- Conflicts with the 3A proposal, listed for your decision (REPO-STRUCTURE.md R1-R3): token claims for audience/role/school conflict with the "`sub` + `sid` only" rule (`CLAUDE.md`, `docs/decisions.md` 2A); zod schemas in `shared-types` would duplicate the API's `class-validator` DTOs; "Next.js" for `apps/web` is still an open decision (`docs/decisions.md` Open #1); parent routes need a second access path in the school guard.
- Phase B: schema and RLS are per table and per role, never per app; the screen-to-table matrix gets an "API audience" column (School App / Student App - Student / Student App - Parent); `push_tokens` records which app a token belongs to.
